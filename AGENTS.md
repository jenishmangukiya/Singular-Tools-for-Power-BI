# AGENTS.md

## Overview
- .NET 10 / WinUI 3 (Windows App SDK 2.4) desktop toolbox for Power BI Desktop authors. Opens on a Home launcher; tools plug in via `IToolPage` + `ToolRegistry`.
- Solution is `SingularTools.slnx` (XML solution format, not `.sln`).
- `src/SingularTools.Core` — `net10.0`, cross-platform, no WinUI. PBIR/PBIP parsing, page model, edit history, Power BI window detection.
- `src/SingularTools.App` — `net10.0-windows10.0.26100.0`, unpackaged WinUI 3 exe. **Root namespace is `SingularTools_App` (underscore), not the folder name.**
- `tests/SingularTools.Tests` — xUnit, references Core only. `.github/workflows/release.yml` runs them on every push to `main`; otherwise verification is local.

## Commands
- Build app: `dotnet build src/SingularTools.App/SingularTools.App.csproj`
- Run app (unpackaged, launches GUI): `dotnet run --project src/SingularTools.App/SingularTools.App.csproj`
- Test all: `dotnet test SingularTools.slnx`
- Single test: `dotnet test tests/SingularTools.Tests/SingularTools.Tests.csproj --filter FullyQualifiedName~NaturalSort`
- No lint/format/codegen config; the compiler is the only check.
- Publishing latest release `dotnet publish "src\SingularTools.App\SingularTools.App.csproj" -c Release -o "$env:LOCALAPPDATA\SingularTools"`

## Test fixture gotcha (read before touching tests or the demo report)
- `tests/SingularTools.Tests/TestReports.cs` owns synthetic PBIR fixtures: `TestReport`/`TestPage`/`TestVisual`/`TestProjection`/`TestSemanticModel` build a throwaway `<name>.Report` (+ optional sibling `.SemanticModel`) under the temp folder, and `TestReports.Visual(...)` discovers a `visual.json` by type/page. **No test reads the checked-in `Demo PBI Report.Report` any more** — it used to, and `dotnet test` went red whenever the demo report was re-saved from Power BI (page count, page names, hardcoded page/visual ids, and later a full table rename to `RAW_DATA` that deleted `financials.tmdl`). Every fixture is now built per test, so the demo report can be edited freely. `SortByColumnServiceTests`/`SemanticModelIndexTests` build their own TMDL via local `Tmdl(...)`/`CreateModel(...)` helpers; add to those rather than re-introducing a dependency on the demo project.
- Anything that must exercise real PBIR/TMDL shapes should generate that shape synthetically (see `SortByColumnServiceTests.CreateSiblingProject` for a `.pbip` + `.Report` + `.SemanticModel` triple, or `TestReports.TestSemanticModel`). Tests that mutate still copy to temp first; read-only tests no longer read a shared fixture at all.

## Architecture
- Add a tool: implement `src/SingularTools.App/Shell/IToolPage.cs` and append a descriptor in `Shell/ToolRegistry.cs`; `MainWindow` builds navigation automatically. One folder per tool under `Tools/`.
- Report state is shared: `App.Workspace` (`Shell/ReportWorkspace.cs`) owns the single `ReportManager` + `ReportEditHistory` for the whole app. Tools must read/open reports through it (`OpenReport`, `Reload`, `Commit`) instead of constructing their own `ReportManager`; it raises `Changed` when the session updates. The Home page opens reports via `ReportPicker.PickReportFolderAsync`; RPM's empty state routes users back to Home.
- **Mutate only via `App.Workspace.ApplyEdit(...)` / `ApplyEditWithResult(...)`** (or `ApplyEdit(..., managerWritesInternally: true)` for methods that already save) — never raw `ReportManager.SaveChanges()`. `ApplyEdit` also saves, commits history, and re-syncs. `ReportFileWatcher` auto-reloads the session when Power BI saves to disk (debounced ~600ms) and an on-disk "signature" suppresses its own writes; an external reload **resets undo history**, so `Undo`/`Redo` disable after an external change. A second `ReportFileWatcher` (`*.tmdl`, filters are configurable) watches the sibling `.SemanticModel/definition` and raises `Workspace.ModelChanged` (model-only; never touches page state/history). Model-editing tools call `App.Workspace.NotifyModelFilesChanged()` after saving so their own writes don't echo back; `MainWindow` toasts on `ModelChanged`.
- Transient feedback must go through `ToastService.Show(...)` (`Shell/ToastService.cs`), never a page-local `InfoBar`/`TeachingTip`. `MainWindow` renders toasts as a non-interactive overlay (`ToastHost`) pinned bottom-right so they never reflow or intercept the page.
- Power BI sync is two-directional and serialized by `Shell/PowerBiSyncService` off the UI thread: **save** (click Desktop's ribbon Save so its unsaved edits hit disk) and **apply** (click the external-changes banner after we write). On the **first activation** `Shell/StartupSyncService` runs a one-shot handshake — it shows the blocking `StartupOverlay` (a `ProgressRing`), saves Desktop, and waits (watcher events restarting a ~1s quiet timer, hard-capped at 10s) until the pages/model watchers have settled, then refreshes the active tool; it is a fast no-op when Power BI Desktop isn't running or multiple reports are open. Later focus gains use the throttled `MainWindow.MaybeRequestPowerBiSave()`.
- `ReportManager` is the whole PBIR layer. A folder is a valid report when `definition/pages/pages.json` exists. Page IDs are 20-char lowercase hex; `DuplicatePage` generates random 10-byte IDs and deep-copies the page folder. `Reload` and `SaveChanges` both run `EnsureValidActivePage`, so a stale `activePageName` (e.g. one Power BI deleted) is corrected to the first page rather than persisted — Power BI otherwise rejects it as "ActivePageName not found". `DeletePage` rewrites `pages.json` **before** deleting the page folder so Power BI never reads a definition that references a folder already gone.
- Writes are atomic: `SaveChanges` writes `pages.json.tmp` then `File.Move(..., overwrite: true)`. Call `SaveChanges()` after mutating `Pages`, and `Reload()` to re-read from disk.
- `ReportEditHistory` is snapshot-based (full copies under `%LOCALAPPDATA%\SingularTools\history\<guid>\NNNN`), not command-based: `Reset` baseline, `Commit` after each edit, then feed the dir from `Undo()`/`Redo()` to `RestoreFromSnapshot`. Each snapshot holds the pages directory under `pages/` plus any nominated outside-the-pages files under `extras/` at their report-relative path; `RestoreFromSnapshot` probes for `pages/` so snapshots written before that layout still restore. Snapshots are **session-scoped** — a new GUID per `ReportEditHistory`, wiped by `Reset` and deleted on `Dispose`, so closing the app or an external reload loses undo/redo (that is why the buttons grey out after Power BI saves). **Undo/redo must go through `ReportWorkspace.Undo()`/`Redo()`, never `ApplyEdit(m => m.RestoreFromSnapshot(...))`**: `ApplyEdit` calls `Commit()`, and a commit means "a new edit happened from here", which truncates the redo branch and leaves Redo permanently disabled. `ReportWorkspace.RestoreSnapshot` recomputes the signature without committing, which is also what stops the watcher reading the restore as an external change and resetting history.
- `PowerBiDetector` identifies Power BI by process name `PBIDesktop` (window title alone is unreliable). `PowerBiNavigator` drives the open report's page tabs via UI Automation (App csproj adds `Microsoft.WindowsDesktop.App` framework reference).
- Model-editing tools follow a distinct path from page edits: `SortByColumnService` (sort orders) and `OlsService` (object-level security roles in `definition/roles/*.tmdl`) read/write TMDL directly, snapshot files through `ModelBackupStore` (project-keyed, **scoped per tool** so one tool's Undo cannot revert another's apply), then call `PowerBiPublisher.TryApplyExternalChangesInPowerBI()`. They deliberately bypass `App.Workspace.ApplyEdit`, which is pages/`ReportEditHistory` only. A role may carry both RLS filters and OLS rules (the "can't combine" restriction applies to a *user* who is in multiple roles); hiding a table must not break a relationship chain, which `OlsService.Validate` warns about. `OlsService` round-trips single-line and fenced/multi-line DAX filters verbatim, and understands the TMDL default-property shorthand Power BI emits for column OLS (`columnPermission X = none`, i.e. `MetadataPermission`) alongside the expanded `metadataPermission:` form. `SortByColumnService.LoadModel` is the single table reader and excludes only auto-generated tables marked `isPrivate` (e.g. `DateTableTemplate_*`); tables marked only `isHidden` (e.g. `LocalDateTable_*`) are still shown, matching Power BI's model view. `OlsService.PreviewRole` renders a role with staged changes applied (no disk write) so the OLS page can show a live OLS/RLS badge; `RoleItemViewModel` seeds its labels in the constructor so every role in the list is badged on load, not just the selected one.
- **Field Repair** (`Tools/FieldRepair` + `BrokenVisualService`) finds every place the report binds a field the model no longer resolves — the state a source-system column rename leaves — and repoints them. The tool is named for what the author does, not for one of the four places it looks: visuals, visual filters, page filters and the report filter. The Core types keep their domain names (`BrokenVisualService`, `BrokenField`, `BrokenVisualReport`) because they describe the problem rather than the product. It is a **pages** tool: `visual.json` and `page.json` live under `PagesDirectoryPath`, so it goes through `App.Workspace.ApplyEdit(..., managerWritesInternally: true)` and gets undo for free; do **not** give it a `ModelBackupStore` scope. Detection is a single recursive walk of each visual (`VisualQueryReader.EnumerateFieldRefs`) keyed on the innermost `{Expression.SourceRef.Entity, Property}` shape, which finds data roles, `sortDefinition` **and** `objects.*[].selector` colour rules in one pass — a queryState-only scan reports a visual as healthy while its conditional formatting is silently inert. `selector.metadata` series keys are plain `"table.field"` strings and need the separate string-based pass. It also scans `page.json`/`report.json` `filterConfig`, and **visual-level filters**, which PBIR writes at the **root** of `visual.json` as a sibling of `visual` — not inside it. Checking only `visual.filterConfig` made every visual filter classify as the vague "Other part of visual". A filter names its column **twice**: the canonical `field` binding (table named directly) and again in `filter.Where` through a table alias declared in `filter.From`, whose `SourceRef` has `Source` instead of `Entity`. The generic field walk resolves only the first, so `BrokenVisualService.RemapFilterBodies` runs **before** it and resolves each alias back to its table to keep both copies in step; it also repoints `From[].Entity` when the table itself was renamed. Order matters: the filter pass identifies a filter by reading its own `field`, so renaming that first would make every filter unmatched. **Report-level filters are repaired too** — `definition/report.json` sits outside `PagesDirectoryPath`, so `ReportWorkspace.OutsidePagesEditTargets` nominates it and `ReportEditHistory` snapshots it under `extras/` (pages go under `pages/`; `RestoreFromSnapshot` probes for that folder so pre-existing snapshots still restore). Without that, an Undo would revert the visuals but leave the filter repaired. Repairs rewrite the binding *and* the cached `queryRef`/`nativeQueryRef`/`metadata` by **whole-token** substitution (`BrokenVisualService.ReplaceToken`), because regenerating from the aggregation enum would mean reimplementing Power BI's display conventions and a loose replace would corrupt a neighbouring column like `SegmentCode`. Usage rows group by a composite key (visual id / `page:<id>` / `report`) — grouping on the visual id alone merged a page filter and a report filter into one row and hid the page filter's label behind the report filter's heading. Model-side resolution is `SemanticModelIndex`, which includes `isPrivate` tables (unlike `SortByColumnService.LoadModel`) since a visual can legitimately reference an auto date table, and resolves **measures** as well as columns. Case-only renames are deliberately *not* reported: field lookup is case-insensitive, so `Segment` → `segment` breaks nothing. The page re-scans automatically on `App.Workspace.ExternalChangeDetected` **and** `ModelChanged` — a model refresh is precisely what breaks a visual after a rename, so a list left on screen would be stale exactly when the author is looking at it. Auto-scans are coalesced (`_scanning`/`_rescanQueued`, because a refresh fires a burst of watcher events) and skip the 1-second minimum-feedback delay that manual scans use. It tracks `_indexedReportPath` and rebuilds `SemanticModelIndex` whenever `ReportPath` changes, or a report opened from Home after the page was built would be resolved against the previous report's model. Undo/Redo call `App.Workspace.Undo()`/`Redo()` and re-scan afterwards, so the list never describes the pre-undo state.
- `VisualQueryReader` is the shared PBIR field-binding reader (extracted from `SemanticColorService`, which now delegates): `TryGetFieldIdentity`, `ExtractProjections`, `EnumerateVisualFiles`, and `EnumerateFieldRefs`. Any new tool that needs to know which model fields a visual depends on should use it rather than re-parsing `queryState`. Note `visual.objects.title` is written by Power BI as a **single-element array**; indexing it as an object throws inside a `catch`, which silently cost `ReportManager.GetPageVisuals` its `DisplayTitle` until `TryReadTitleText` was added to accept both shapes.
- `ReportManager.DiscoverReportFolder`/`FindReportByName` hardcode `e:\Test_Projects\Singular Tools for Power BI` fallbacks — a dev-machine quirk, not portable.
- App logs to `%LOCALAPPDATA%\SingularTools\app.log` via `App.Log`; check it for launch/XAML failures since failures in a GUI are otherwise silent.
- App is unpackaged WinUI (`WindowsPackageType=None`, self-contained Windows App SDK, custom `Program.Main` with `DISABLE_XAML_GENERATED_MAIN`). Do not remove the `CopyXamlResourcesToPublish` / `CopyAssetsToPublish` targets — `dotnet publish` omits `.xbf`/`.pri`/Assets for unpackaged WinUI, and an installed copy then silently runs stale UI without icons.

## Distribution
- `.github/workflows/release.yml` runs the test suite, then `build-installers.ps1` for all three arches, on every push to `main`. It maintains a single **rolling** pre-release (tag `latest-build`): the previous release is deleted with `--cleanup-tag` and recreated, so exactly the 3 Setup.exe assets are attached and the tag tracks the latest commit. Installer version is `1.0.<run_number>`.
- `distribution/register-external-tool.ps1` publishes Release to `%LOCALAPPDATA%\SingularTools\`, regenerates `distribution/SingularTools.pbitool.json` (absolute exe path + base64 icon), then self-elevates to copy it into Power BI's `External Tools` Common Files directory.
- `distribution/register-as-admin.cmd` only copies the already-present JSON (no publish); requires admin.
- `distribution/installer/build-installers.ps1` builds per-arch per-user installers: it publishes self-contained `win-x64`/`win-x86`/`win-arm64` (via `-r`, overriding the `.csproj` arch default) into `distribution/installer/publish/<arch>`, then runs Inno Setup (`ISCC.exe`) on `SingularTools.iss` with `/D` defines (`ArchName`, `ArchitecturesAllowed`, `AppVersion`, `AppSourceDir`, `OutputDir`, `IconData`). Output: `distribution/installer/output/SingularTools-<version>-<arch>-Setup.exe`. Needs Inno Setup 6 (`winget install JRSoftware.InnoSetup`; the resolver also checks `%LOCALAPPDATA%\Programs\Inno Setup 6`). `output/` and `publish/` are gitignored.
- Installers are per-user (`PrivilegesRequired=lowest`, `DefaultDirName={localappdata}\SingularTools`), create Start Menu/desktop shortcuts, and offer a "Register with Power BI Desktop" task. `SingularTools.iss` rewrites the manifest's `path` to the installed exe at `ssPostInstall`; `register-pbi-tool.cmd` (shipped into `{app}`) writes the per-user JSON and copies it into Common Files, self-elevating via `net session` + `Start-Process -Verb RunAs` when needed. `[UninstallRun]` calls the helper with `-Unregister`. Unsigned for now (`SignedUninstaller=no`), so SmartScreen warns.
- The External Tools manifest needs `iconData` (a `image/png;base64,` data URI) or Power BI shows no ribbon icon. `build-installers.ps1` bakes it into the `.iss` via `/DIconData` (binary-safe encode in PowerShell, not Pascal), sourcing `Assets\Square44x44Logo.targetsize-48_altform-lightunplated.png`. `register-pbi-tool.cmd` builds the same value at runtime in PowerShell from that same file.
